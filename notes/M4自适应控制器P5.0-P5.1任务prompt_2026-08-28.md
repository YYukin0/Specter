## P5.0 — GammaTune 算法实现（M，预估2天）

依据：`notes/project_plan_v9.md` §7 P5.0（第172-173行）+ 附录 A.2（第430-450行，含成本模型、Algorithm 1、三轮手算算例）+ 参考文献 Kim et al. 2025（arXiv 2504.00030，第566行）。

**成本模型**（背景，理解用，不强制实现）：
```
cost = N / (α·γ + 1) × (c + γ) × T_draft,   c = T_target / T_draft  （典型 4-10）
```

**Algorithm 1（逐字对照附录 A.2，不要凭记忆推导）**：
```
# 每轮投机结束后，拿到本轮实际接受数 A（= StepResult.n_accepted），更新 γ：
if A == γ:                       # 上一轮全部接受，可能还有余量 → 快速扩窗
    γ ← A + δ
else:                            # 没全接受 → 回落到 EMA 的保守估计
    γ̄ ← clip(γ_min, γ_max, (1-η)·γ̄ + η·A)
    γ ← ceil(γ̄)
# 注意：扩窗分支不更新 γ̄；扩窗后的 γ 也要再 clip 到 [γ_min, γ_max]
```

**三轮数值算例**（η=0.3, δ=2, γ_min=1, γ_max=10, 初始 γ̄=3, γ=3，附录 A.2 的表）：

| 轮次 | A | 分支 | 计算 | 新 γ̄ | 新 γ |
|---|---|---|---|---|---|
| 1 | 3（A==γ） | 扩窗 | γ ← 3+2 | 3（不更新） | 5 |
| 2 | 2（A<γ） | EMA | γ̄ ← clip(1,10, 0.7×3 + 0.3×2)=2.7 | 2.7 | ceil(2.7)=3 |
| 3 | 3（A==γ，此时 γ=3） | 扩窗 | γ ← 3+2 | 2.7（不更新） | 5 |

**关键实现检查点**：
- **A==γ 的判定用的是"进入本轮时的 γ"**，不是别的。第 3 轮 A=3、γ=3 → 触发扩窗 → γ ← 3+2=5。别写成拿新 γ̄ 判断。
- **扩窗分支不碰 γ̄**。只有 EMA 分支更新 γ̄。第 3 轮之后 γ̄ 仍是 2.7。
- **扩窗后 clip**：`γ ← clip(γ_min, γ_max, A+δ)`。A=γ_max 时 A+δ 会超 γ_max。
- **γ̄ 是浮点、γ 是整数**（`ceil`）。两个状态量都要跨轮持有。
- 把这个三轮算例写成 `tests/test_gammatune.py` 里的单元测试：一个纯函数 `gammatune_update(gamma, gamma_bar, A, *, eta=0.3, delta=2, gmin=1, gmax=10) -> (new_gamma, new_gamma_bar)`，喂 A=[3,2,3]，断言 `(γ, γ̄)` 逐轮等于 `(5,3.0) → (3,2.7) → (5,2.7)`。这是 P5.1 和 P5.4 之后要引用的"已知正确"参照点。浮点比较用 `abs(... ) < 1e-9`。

**实现落点建议**：
- `src/gammatune.py`，导出：
  - `gammatune_update(...)` 纯函数（上面那个，单测直接测它）。
  - `GammaTuneConfig` dataclass（eta/delta/gmin/gmax/gamma_init/gamma_bar_init，默认 = 论文值）。
  - `gammatune_generate(prompt, draft, target, tokenizer, *, config=GammaTuneConfig(), max_new_tokens=64, temperature=1.0, seed=0, carry_state=None, apply_chat_template=True) -> GammaTuneResult`
    —— 复用 `speculative_step`（**不要重写 rejection sampling**），每轮用当前 γ 调一次 `speculative_step`，拿 `n_accepted` 过 `gammatune_update`，更新 γ/γ̄ 进下一轮。块内 EOS 截断照 `speculative_generate` 的写法（坑13）。
    `carry_state` 参数：允许把 (γ, γ̄) 状态**跨 prompt 传递**（P5.1 波动序列需要控制器不在每条 prompt 边界重置）。默认 `None` = 每次从 config 初值开始。
  - `GammaTuneResult`：`text`、`token_ids`、`accept_lengths`（每轮 n_accepted）、`emitted_per_round`、`gamma_trace`（每轮进入时的 γ，列表）、`n_rounds`、`elapsed_s`、`final_state=(γ, γ̄)`、`mean_emitted_per_round`、`mean_accept_length`。
- `src/verify_gammatune.py`（P5.0 的实验驱动）：
  - 对 `src/prompts.py` 的 8 条 prompt，采样模式（temperature=1.0），**≥3 次跑取均值±标准差**（§9.6 风险2，seed=0/1/2），跑 GammaTune 和固定 γ∈{1,3,5,7}。

  - **成功判据**：GammaTune 的 `mean_emitted_per_round` ≥ 最优固定 γ 的 `mean_emitted_per_round`（允许在 1 个 std 内打平——GammaTune 论文自己也只有 1.15x，且承认低方差场景收益有限，坑9）。如果 GammaTune 明显低于某个固定 γ，如实写"在这对模型 / 这批 prompt 上 GammaTune 未跑赢固定 γ=X"，并给一句可能的原因（比如 α 太稳定、方差不够大，正是坑9 描述的场景）。**不要为了达标改指标口径或调超参**。

- 关于 GammaTune+ 变体（logit 提前停止阈值 τ）：**不实现**，不在 P5.0 范围（附录 A.2 明确）。

## P5.1 — 波动场景鲁棒性测试（S，预估1天）

依据：`notes/project_plan_v9.md` §7 P5.1（第178-179行）+ §9.6 坑9（第244行）+ §13 走读示例（第346行）。

**坑9**：GammaTune 论文自己在 Limitations 里承认——draft/target 匹配度高（方差小）时收益有限；依赖历史接受率使它在**对抗性 / 剧烈波动场景**下退化。P5.1 就是专门设计一个非稳态场景，看 GammaTune 到底是还有优势，还是像论文承认的那样收益打折。

**要做的事**：
1. **构造一个混合 prompt 序列**（新文件 `src/nonstationary_prompts.py`）：一段代码生成任务 + 一段开放聊天，**中途切换任务类型**，控制器状态跨 prompt 连续（用 `gammatune_generate` 的 `carry_state`）。建议结构：
   - 段 A：6-8 条代码/结构化生成 prompt（写函数、补全、重构、命令行单行、JSON 输出——代码类 α 通常更高，投机解码更划算，是"生产界共识"里 α 高的那一侧）。
   - 段 B：6-8 条开放聊天 prompt（解释、总结、创意写作——自由文本 α 通常更低）。
   - 序列排布至少测两种：`A→B`（一次切换）和 `A→B→A`（切回去，测控制器能不能恢复）。可以再加一个 `交替 ABABAB`（高频切换，更接近对抗性）。
   - prompt 内容自己写，中性主题，别抄版权文本。代码类可以参考 `src/prompts.py` 已有 3 条的风格扩写。
2. **对照组**：同一个序列上跑固定 γ∈{1,3,5,7} 和 GammaTune，同样 ≥3 seed。
3. **测什么**：
   - 整条序列的 `mean_emitted_per_round`（GammaTune vs 各固定 γ），以及**只在切换点后若干轮**的窗口指标（切换后 GammaTune 的 γ 多快调整过来）。
   - `gamma_trace` 画出来（存进 JSON，必要时 ASCII 或存成可画的数组）——看 γ 在段 A（高 α）是不是升上去、切到段 B（低 α）是不是掉下来、切回段 A 能不能回升。这是附录 A.2 说的"扩窗要快、收缩要稳"在非稳态下的行为验证。
   - 和稳态场景（P5.0 的结果）对比：GammaTune 的相对优势在波动场景是变大、持平还是缩小。
4. **结论怎么写**：
   - 如果 GammaTune 在波动场景仍 ≥ 最优固定 γ：说明它的 EMA + 快速扩窗设计在这种程度的非稳态下够用，给出 γ 轨迹作为证据。
   - 如果 GammaTune 在波动场景**落后**于某个固定 γ：这不是失败，是复现了坑9 / 论文 Limitations 说的现象——如实写"在 XX 切换频率下 GammaTune 收益打折/为负"，这本身是一个诚实的发现，支撑"为什么还需要 P5.3 的 batch-aware 逻辑 / 更强的场景感知"。
   - 结果写 `results/p5_1_nonstationary.json`。

**为什么这步不能跳过 / 不能只做稳态**：§13 走读示例第346行明确——P5.1 就是用来检验控制器在"部分任务性质变了、部分没变"这种混合场景下是否按预期反应；只测稳态场景等于没测 GammaTune 最可能出问题的地方。

## P5.3 — Batch-aware 熔断器（M，预估2天，本次可选，见"已确认决策点"第4条）

依据：`notes/project_plan_v9.md` §7 P5.3（第184-186行）+ §9.6 坑11（第246行）+ 坑12（第248行）。若这次做，要点：
- 高 batch 时自动降级/禁用投机解码。
- **必须含**周期性重探测机制（避免 DSD 式"关了就不再收集数据、难以重启"，坑11）——比如每 N 步强制插一次小 γ 试探，把结果记在 per-task 粒度而不是全局一刀切。
