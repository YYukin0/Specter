### P2.1 全模型 fake-quant
Qwen2.5-1.5B-Instruct 196 个目标 Linear：**192 层量化 / 4 层回退 fp16**（layer 13-14 `mlp.down_proj`、layer 19-20 `self_attn.o_proj` —— 网格里"不缩放"赢了，诚实回退不是 bug）。α 直方图集中 0.3–0.6（0.4 峰 71 层，0.5 次 57 层）。逐层输出 MSE 相对"不缩放"改善中位数 **+28.3%**（min +0.8% / max +99.9% / mean +30.7%）。计时：激活捕获 3.1s + 搜 α & 量化 31.6s。真实 int4 打包仍留云端。

### P2.2 跨分布鲁棒性 —— 🟡 部分复现
矩阵 {calib=NL, calib=code} × {eval=wikitext2, eval=mbpp_code}，n_calib=32，512-tok 行，3 shuffle。**代码语料用 mbpp 替代**（codeparrot / c4 本地缓存实际只有 README 快照，`HF_HUB_OFFLINE=1` 拉不到 —— 坑17）。

fp16 基线：wikitext2 **12.18** / mbpp **3.11**。

| | eval=wikitext2 (NL) | eval=mbpp (code) |
|---|---|---|
| calib=NL（同/跨）  | +1.212（同分布） | +0.190（跨分布） |
| calib=code（同/跨） | +1.773（跨分布） | +0.166（同分布） |

- **eval=code 上**：跨−同 = +0.024，不显著 → AWQ「跨分布几乎不掉」成立。
- **eval=NL 上**：跨−同 = **+0.56**，跨分布 cell std 仅 0.06，区间不重叠 → 在 NL-eval 上**不成立**。
- 反向复核（§9.6 风险4）：两校准集（wikitext 段落 vs mbpp 函数）token Jaccard ~0.03，确实不重叠，penalty 真实存在；但 mbpp 解法是 3–8 行模板函数，比真实代码窄得多，**+0.56 里有一部分是 mbpp 语料过窄的假象**（也是为什么 code-eval 的 fp16 基线低到 3.11）。
- Michael 3B 那份方向参照：他测的跨−同 ≈ +0.24，但 3B / bf16 / 他自己的 AWQ 实现 / 更长校准行，前提不同，只做方向参照。

**结论**：AWQ 跨分布鲁棒性在 code-eval 复现、NL-eval 不复现。没有自研 GPTQ，§4.3 claim 的对比半边留云端。

### P2.3 校准集大小消融 —— 🟡 不是干净复现（有真实拐点）
n_calib ∈ {4, 8, 16, 32, 64}，calib=NL 固定，每行截断 64 tok，per-layer 上限 = n_calib×64，3 shuffle，wikitext2 ppl。

**踩坑16（§9.6 风险4 教科书案例）**：首轮 `_quantize_fresh` 把捕获上限写死 512（P2.2 默认值），而 `capture_all_layer_inputs` 一旦每层都攒够 512 token 就 `break` —— 头 1–2 条 512-tok wikitext 行就填满，于是 n_calib ∈ {8,16,32,64,128} 喂进**逐 bit 相同的池子**，seed 0 每个 size 都是 ppl 13.6015。这条平坦曲线**恰好长得像** AWQ「小校准集就够」的预期结果。已杀掉重跑（pid 46916 → v2），上限改成随 n_calib 线性增长，`capture_knob_actually_moved=true` 确认这次真的动了。

修正后（mean±std）：

| n_calib | wikitext2 ppl | delta vs fp16 |
|---|---|---|
| 4  | 13.57 ± 0.39 | +1.39 |
| 8  | 13.45 ± 0.02 | +1.27 |
| 16 | 13.32 ± 0.06 | +1.14 |
| 32 | **13.25 ± 0.02**（最优） | +1.07 |
| 64 | 13.31 ± 0.02 | +1.13 |

knee(4−64) = +0.25 ppl，小样本 shuffle 方差 ~19×。**不干净复现** AWQ「a handful of sequences is enough」/ Michael 3B 平坦曲线：本机 1.5B fp16 下要到 n_calib=16–32（~500+ 捕获 tok/层）才稳，更小既偏高又方差大。如实记录，未调参。
n_calib=128 去掉：8192 tok/层 × ~509k 汇总 in-features × 4B ≈ 17GB CPU 端捕获，会把 24GB 机器打爆；再往上需要把 `capture_all_layer_inputs` 重写成逐层量化即时释放。

**一句话结论**：自研 AWQ 管线数值对、全模型跑通、能采统计、能搜缩放因子；但把它当"论文结论复现器"时，P2.2 和 P2.3 各有一处在本机 1.5B fp16 setup 下不成立，都已如实写进结果文件和 §9.3。

**留给用户的决策点**：
1. **自研 4-bit AWQ 的 ppl 代价 ≈ +1.07（fp16 12.18 → 13.25，n_calib=32，最优点）**。这是 fake-quant（fp16 浮点落在 4-bit 网格上），不含真实打包的额外误差；真实 int4 + GPTQ 对比留云端。这个 +1.07 是否可接受、要不要继续投入调（group size / 混合精度回退更多层 / per-tensor→per-channel zero-point），用户定。
2. **P2.2 的 NL-eval +0.56 跨分布 penalty 有多少是 mbpp 语料窄的假象** —— 要判清必须换真实代码语料（codeparrot-clean / the-stack 子集），这只能云端做。是否值得为这一条单独排云端时间，用户定。
3. **codeparrot / c4 / 自研 GPTQ 那半** —— 明确留云端 M7/M8。
4. **n_calib≥128 + 逐层量化重写** —— 需要重构 `capture_all_layer_inputs`，本地不做，用户定优先级。

| batch | tok/每次 target 前向 | mean tok/seq/round | tok/s（无 KV cache，仅趋势） | 峰值显存 | α |

| 1 | 2.82 ± 0.18 | 2.85 | 11.4 | 4135 MB | 0.779 |

- 每次 target 前向的 token 产出**随 batch 近线性上升**（batch 摊薄 target 前向成本，符合预期）。

**一句话结论**：批量实现正确（parity 契约达成），本地小 batch 段看不到批处理带来的投机效率损失。真正的吞吐交叉点需要带 KV cache 的大 batch（云端）。
